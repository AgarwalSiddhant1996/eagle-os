# Product

## Platform

Web UI, primarily inside a host canvas; standalone local preview is a secondary path.

## Users and purpose

Eagle OS serves product managers. They need a small review point for decisions, evidence, work ownership and follow-ups, without reconstructing context across conversations.

## Confirmed product direction

The approved interface is a polished everyday operating workspace: compact briefing, clear decision cards, follow-ups, work detail and evidence history. First run must guide the user through focused steps, not expose a long form or require finding a setup tab.

The user steers from a main chat. Native onboarding can dispatch scoped discovery and connection checks through the supported host SDK. Typed results populate source bindings and workstream owner state. Separate approved requests cover source collection, owner preparation, schedule configuration and read-only worker checks. Actual source, messaging, scheduler and remote capabilities belong to the host and must be checked, not assumed.

Day one exposes Today, Work and Improvements. Settings holds Connections, Automation, Skills and optional Remote. A PM can request a source-bound domain tab, review the exact safe manifest and add it locally. No safety, release or workstation dashboard is required.

## Constraints

- Original neutral implementation and synthetic examples only. No account, employer, product workspace, endpoint, credential or personal defaults.
- Local mutable state and skill installations remain outside the code folder. Existing user/global skills cannot be overwritten.
- Preserve existing workspace data and explicit model choices. A recorded update or accepted message is not a verified outcome.
- External sends/writes are not implemented and must not be implied by local decisions.
- Match the established everyday dashboard quality through semantic light/dark themes, clear hierarchy and familiar controls, without copying private assets, content or implementation.

## Acceptance

An unconfigured workspace inventories available tool and configured repository names before asking for source access. Available entries start checked; missing, unknown or sign-in-needed entries stay separate and unchecked. Connect all selected locks the selected identities and read-only consent. The manual demo remains separate.

Inventory cannot ingest content, inspect credentials or prove authentication. Connected setup shows actual progress/access failures and matching host callbacks before claiming source access. It never substitutes synthetic evidence for a real connection. A configured workspace opens Today. Work, owners, exclusions, tasks and evidence survive reload. Skills live in setup/settings with truthful activation status.

An actual isolated owner, approved skill guidance access, bounded source evidence and a returned source-backed result establish on-demand readiness. A saved/read-back schedule is only configured; daily verification also requires actual provider scheduled-trigger proof and a changed-owner return. An empty queue, accepted prompt or installed skill does not prove readiness.

## Open integration boundaries

Supported local host session tools perform actual actor routing. SDK admission alone never creates an owner. External sends, cloud owner callback transport, live custom-record adapters and remote-worker execution remain separate unimplemented capabilities.
